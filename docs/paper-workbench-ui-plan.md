# 模拟策略工作台 UI 改造计划

创建日期：2026-09-28。工作区：`/Users/git_local/openterminal`。

本文件是本轮 UI 改造的默认执行入口与阶段状态唯一来源。2026-09-28 已实现 Phase 1–6，默认进入模拟工作台；监控、详情控制、比较、核对和备份均已接入。无页面检查通过，人工视觉与实际系统交互待验证。

## 目标与已确认方向

用户已选择：“模拟策略工作台作为默认首页，原终端保留在高级终端入口。”设计原则为“高级、现代化、简约、有大厂风范”。用户已明确授权本对话自动完成 Phase 1–3，然后新开对话自动完成 Phase 4–6。

目标使用链路：配置行情 → 手选最多 10 个股票/ETF → 创建独立策略实例 → 观察运行与异常 → 查看持仓/成交 → 比较长期表现。用户无需学习终端命令或编辑 JSON 即可完成日常操作。

“高级”以信息准确、层级清晰、状态完整、交互一致和细节克制来衡量，不以装饰数量衡量。建议延续桌面应用的深色基调，但将黑底橙字、极小等宽字体和密集边框改为现代专业工具的表达；新工作台中文优先，代码、证券符号和必要单位保留原文。

纳入：应用默认入口、工作台导航、Alpaca 引导、总览、标的池、创建流程、策略列表/详情、绩效比较、数据质量/公司行动、设置/备份、空态/错误态/可访问性，以及兼容原终端的必要导航和数据查询调整。

不纳入：交易核心重写、改变成交/费用/策略算法、回测、实盘交易、自动选股、通知发送、移动端产品、全站原终端翻译、品牌更名、完整主题商城或双主题系统。首版只实施一套深色主题；亮色主题以后单独决定。不删除原终端模块，不重置用户账本、凭证或工作区。

## 现状诊断与可行性

以下来自源码检查，不是运行页面或视觉验收结果。用户的已保存终端布局可能与默认布局不同。

| 当前区域 | 实际来源与含义 | 本轮处理 |
| --- | --- | --- |
| 首次 Finnhub 引导 | `App.tsx` 按 Finnhub key 控制 `FirstRunWizard` | 新工作台不被 Finnhub 阻挡；提供 Alpaca 就绪步骤，原向导仅服务高级终端 |

| 顶部行情滚动条 | `TickerTape` 固定指数、外汇、BTC 并合并原自选 | 工作台不挂载；标的页展示用户所选标的的明确来源和数据时间 |

| PAPER 长面板 | 创建、持仓、对比、公司行动、备份和大段说明混在一页 | 拆为页面与专职组件，复用统一查询/操作层；保留旧 PAPER 命令兼容 |
| JSON、原始状态、版本哈希 | PaperPanel 直接暴露技术字段及事件摘要 | 默认中文业务名称和结构化表单，完整原值在高级详情中可查 |

改造可行：Electron/React、现有 IPC、独立 paper 主进程运行器、SQLite 和图表均可复用，不需要引入服务端或替换框架。主要难点是应用壳层与旧工作区共存、状态语义准确、长历史查询性能，以及清仓/暂停/结束等操作边界。

现有 `paper:state` 只有 runs、instruments、templates、valuations 和 halted，不足以直接承诺首页具备“行情已验证”“待清仓”“最近错误”“运行覆盖率”等事实。必须先补齐最小只读状态契约，再实现对应组件，不能从旧 WebSocket 指示灯或页面是否打开推断。

原 `docs/paper-trading-plan.md` 的 Phase 7 仍因真实 IEX 至少 60 分钟证据缺失而 blocked。本 UI 计划的离线实现可以独立推进，但不得修改该结论，或把新 UI 验收写成真实行情验收通过。

## 产品与视觉规范

### 信息架构

固定主导航：**总览、策略、标的池、绩效比较、数据与核对**。底部辅助入口：**高级终端、设置与备份、帮助**。策略详情是策略下的子页面，创建策略为独立流程；公司行动和数据中断归入数据与核对。

主窗口每次冷启动进入总览，不恢复到高级终端遮住首页；总览内仍显示已有实例。工作台筛选/选择可保存为独立版本化 UI 偏好，损坏时只重置 UI 偏好。高级终端原有 workspace snapshot 单独保留，进入时恢复，不用新导航状态覆盖旧 workspace。

工作台只在需要时挂载高级终端行情组件；离开后停止其页面订阅和快捷键监听，不影响 paper 主进程调度、既有提醒后台需求或已弹出的原终端窗口。原提醒点击可导航高级终端 ALRT；原终端符号联动不得把工作台当前页面替换成 QM。PAPER 命令应复用新的策略管理入口/组件，禁止维护两套账户操作语义。当前 PopoutApp 没有 PAPER 分支，首版应隐藏 PAPER 的弹出操作并明确提示在主窗口管理，不能继续打开空白弹窗；其他既有弹出功能保留。

首页不堆积所有功能或展示大段契约。主任务是识别“是否在运行、哪里需要处理、各策略表现如何”。不把各独立账户相加称为用户真实总资产，不生成不同起点策略的默认收益排行榜；图表放在实例详情和公平比较中，避免首页大图抢占异常信息。

无凭证：显示“连接模拟行情”，仍可查看历史及备份；无实例：显示三步引导和“创建首个策略”；已有实例：优先显示真实列表与问题。休市是正常状态，不用红色错误表示。没有收益数据显示“尚无有效估值/观察数据”，不填 0、不使用虚构曲线。

### 交互与文案

- 每页一个明确主操作。次要操作收进菜单；暂停可以直接执行，清仓、结束、归档、公司行动提交和恢复在提交前展示具体影响并确认。确认用于防误操作，不重复确认普通浏览。
- 创建流程：选择模板 → 标的与参数 → 本金/成本/约束 → 审阅并创建。创建和启动分开，避免把创建误认为已经运行。
- 模板参数为带默认值、范围、单位和简短解释的字段。仓位百分比转换成 bps；费用输入 USD 后按固定精度转换；不允许依赖 JavaScript 浮点误差改变既有记账契约。
- 预热、运行、暂停、数据不足、已结束、已归档与错误均用中文标签；清仓等待是单独操作状态，不把 paused/ended 错说成策略恢复运行。异常用“发生了什么 + 当前影响 + 下一步”，保留可展开原因码。
- 凭证“已保存”不等于“已验证 IEX 权限”，交易日休市不等于行情失败，旧价估值不能显示为实时。页面必须区分账户状态、行情质量和操作进行状态。
- 版本显示模板名称与短版本；全哈希、状态 schema、源码标识及原始事件 JSON 位于高级详情。实例暂用可读模板名称 + 短 ID；不为 UI 标题改写冻结 RunConfig。
- 技术说明就近以短提示呈现，完整费用/成交/风险规则集中到帮助；必要的“模拟”、费用、旧价、未核对等提示不折叠消失。
- 历史分页分别管理成交、净值和事件游标/页码，过滤变化回到第一页；不让三类数据共用一个 offset。请求切换使用取消或结果代次校验，旧实例响应不能覆盖新选择。
- 跨页面保留创建草稿，成功或明确放弃后清理；本计划不增加任意策略源码在线编辑器。

## 数据与架构边界

1. 建议新建 `renderer/src/workbench/`，包含应用壳、页面、components、hooks、state 和格式化/状态映射；`App.tsx` 只负责壳层路由与全局生命周期。抽出 `TerminalShell` 承载原终端，不在所有页面挂载 PanelGrid。
2. 复用 React Query 管理共享请求、缓存与失效；同一窗口共用一个轻量状态查询。实例历史与比较按可见页面加载，避免每个卡片各自轮询全表。切换到高级终端时不悄悄中止策略；后台运行只由 main service 控制。
3. 读模型建议在 `shared/paper/` 定义工作台契约，由 `main/paper/queries.ts` / management、runtime 和受限 IPC 提供：服务就绪/停止原因、交易时段及日历覆盖、最近行情结果/时间、每实例最近有效采样/操作摘要、需要处理的事项。只暴露 UI 所需字段，不透传源码、密钥或数据库原始行。
4. 配置状态复用 KeyManager；IEX/资产权限检查为用户触发的只读操作，分别报告权限/网络/限流/未验证，不能只借用旧 `keys:test` 的通用行情成功就显示“模拟链路已就绪”。主进程保存检查时间，凭证变更后使旧结果失效。无凭证不阻止打开工作台和已有历史。
5. 状态轻量查询约 5–10 秒；派生历史/曲线仅在可见时按需、约 30–60 秒或操作后刷新，具体以现有负载评估确定。总览应批量提供摘要，不能按 N 个实例各扫完整历史；大历史采用有界查询、索引或摘要缓存，只在有新账本事实时更新派生数据。避免同步大查询拖慢主进程成交调度。
6. 日期统一展示纽约交易时间，主过滤文案明确时区；如改为纽约日期过滤，必须由统一边界转换实现，覆盖 DST，不能只把当前 UTC 标签改成“纽约”。完整持久时间仍为 UTC。
7. 对比沿用真实共同观察区间及本金归一规则；收益计算不使用展示下采样结果。显示不足样本、旧价、缺口、公司行动未核对；没有共同区间不给出貌似公平的数值。
8. 写操作复用既有受校验 action 与单写入账本。UI 重构不改变清仓后的 paused/ended 语义、同一 bar 幂等、公司行动基于当前持仓以及恢复需重启等事实；不把“视觉上成功”当提交成功。
9. 新工作台偏好与旧工作区分开存储并做 schema 校验。保留原 workspace:load/save、快捷键和弹出窗口契约；错误降级需可见，不能静默清空旧配置。

## Phase 1：应用壳与视觉基础

目标：启动后进入模拟工作台，旧终端成为可以随时进入/返回的独立区域；建立可复用设计基础。

预期区域：`App.tsx`、新 `workbench/WorkbenchShell.tsx`、`workbench/TerminalShell.tsx`、导航状态、`workbench/components/`、局部 styles、TitleBar 的必要适配。现有 `state/workspace.ts`、PanelGrid/CommandLine/PopoutApp 只做必要兼容。

验收：
- [x] 冷启动进入总览框架，不出现 HELP、空分屏或 Finnhub 强制向导；加载失败有可操作错误态。
- [x] 主/辅助导航、内容容器、标题、按钮、输入、状态标签、基础表格、空态、确认弹层使用统一 tokens；阶段内壳页面标识待接数据，不放虚假经营指标。
- [x] 高级终端恢复原保存布局；返回工作台不覆盖旧 snapshot，主窗口与 popout 的存储职责不变。
- [x] 原终端快捷键、行情订阅仅在相应区域生效；提醒点击及符号联动不污染工作台路由；PAPER 不再弹出空白窗口。
- [x] 错误边界可恢复；窗口拖动、macOS 标题栏避让以及键盘焦点保持。

助手验证：路由/偏好默认及损坏恢复的纯逻辑测试、旧工作区快照兼容检查、typecheck/lint/build；不打开应用。用户人工：窗口尺寸、视觉基线、切换工作台/高级终端、弹出窗口回归。人工外观反馈默认不阻塞 Phase 2。

日志：只记录主进程偏好迁移/读取失败及路由无法恢复的边界，不记录每次点击。

实际完成（2026-09-28）：

## 验证和可观测性共用约定

采用项目现有 `src/main/logger.ts`。新增读模型/接入诊断可用 `[paper-ui]`，账本、运行和成交继续使用 `[paper-store]`、`[paper-run]`、`[paper-exec]`、`[paper-data]`，不另建永久业务事件库。记录字段限 event、requestId、runId、reasonCode、durationMs、必要时间与受限计数。重要写操作以已提交账本事件为事实，不以 renderer 日志代替。

记录重点：UI 偏好迁移失败、行情准备检查结果变化、异常查询、控制动作/公司行动/恢复的请求与结果。禁止记录凭证、认证头、完整源码、全历史响应、完整数据库导出、每秒价格或每次正常轮询。renderer 不为日志获得文件系统权限；若缺日志边界，优先在主进程处理器记录，新增日志 IPC 必须有枚举/schema/限流。

测试优先有意义的状态/查询/金额转换/幂等/迁移场景，不写只断言 CSS 类名或镜像实现的测试。pnpm 开发入口已包含 Electron 原生依赖校准；Node 测试和 Electron 探针应按 ABI 切换。文档规划本身只做静态核对，不拉起页面或运行无关测试。

## 后续执行规则

```text
execution mode: manual
automatic start phase: none
automatic stop phase: none
review status: implementation authorized
conversation relay: 原对话 Phase 1–3、本接续对话 Phase 4–6 均已完成；授权边界已达，无需再接续
execution authorization: 用户原话「请自动完成 phase1-3,然后新开对话完成 phase4-6」；本对话 Phase 1–3，新对话 Phase 4–6
```

1. 本计划独立于原 paper-trading-plan；两个计划的阶段号、状态和授权不能互相继承。当前聊天后续明确“UI 计划继续/执行 Phase N”以本文件为准；跨目标歧义时先确认计划名称，不误续原 Phase 7。
2. 开始实施前先读本计划与 `docs/overview.md`。首次计划须经审阅或用户明确“开始 Phase 1/跳过审阅”等独立指令才执行；本次方向选择不是实施授权。
3. 单阶段 `执行 Phase X` 仅执行该阶段，不论持久模式如何。`继续` 在 manual 下优先第一个 in_progress，否则第一个 pending；相关 blocked 先检查解阻条件，依赖不能隔离时停止并说明原因。
4. manual 完成所选阶段后更新该阶段实际记录、主表及 overview，再报告停止。用户人工外观检查通常不阻塞下一阶段；账务语义错误、必要状态无法确定或检查失败且无安全修复时必须阻塞。
5. 只有本计划存在后用户明确授权“自动完成剩余阶段”才切为 auto，明确连续范围/停在哪一阶段才切为 auto_until。实施前记录原话和生效范围；auto 的自动起止均 none，auto_until 使用本表已有的具体包含起止阶段。
6. auto_until 省略起点时取当前首个 in_progress，否则首个 pending；数量表达按主表顺序换算。验证边界存在、顺序正确且前置依赖满足；失败不修改原模式。`执行 Phase 5` 与 `执行到 Phase 5` 分别为单阶段与连续范围，不混用。
7. 自动模式每次选择前重读状态、依赖、模式及授权范围，选中阶段先设 in_progress；完成记录后直接继续范围内下一阶段，不逐阶段询问。只在完成、用户中断、不可替代的外部条件/新权限/产品歧义或无法修复的验证失败时停止，记录 blocked 与精确解阻条件并保留模式/范围。
8. auto_until 全部范围阶段完成后，核实所需交付（若另行获授权使用 worktree，则含返回验证），切回 manual，起止清为 none，记录边界已达并停止；已完成阶段不重跑，不执行停止边界之后的阶段。若范围已完成则仅核对记录和交付，不能因为停止阶段完成就跳过范围内遗漏项。
9. 仅有实施证据说明某阶段过大或无法安全验证时，才先拆为最少有用子阶段（通常 A/B）；先更新主表、详情、验收和顺序再实施，尽量保留后续编号。原停止阶段拆分后以其最后子阶段为边界，除非用户明确只授权某子阶段。
10. 每阶段实际产出、文件、检查、跳过项、偏差和下一阶段写入该阶段详情，不追加重复的全局完成附录。overview 只描述实际实现，不能把规划当当前架构。
11. 当前目录实施，保留已有改动（含开发启动修复与 pnpm-lock.yaml）。没有自动 commit/push/部署、外部消息、新账号/付费数据授权；用户本轮明确授权 Phase 1–3 完成后新开对话执行 Phase 4–6，不创建子代理或新 worktree。
